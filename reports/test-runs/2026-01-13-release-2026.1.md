## Which automated tests failed, and why?

### Failure 1: proration rounded a half cent down

- Test: `tests/unit/billing/test_proration.py::test_half_cent_rounds_up`
- What the test does: it prorates a synthetic amount of $10.01 over a 30-day period with 15 days remaining. The exact result is $5.005. The billing rule is "rounded to the nearest cent, half up", so the expected value is $5.01.
- What happened: the code returned $5.00.
- Cause: the proration function used the language's default rounding, which rounds a half to the nearest even digit ("banker's rounding"). The function had been touched while the invoice PDF totals were reworked.
- Fix: the Billing team changed the function to use the half-up rounding helper in `common/money.py`. Two more boundary cases were added (a half cent on a seat credit and on an upgrade charge).
- Customer impact if shipped: a difference of one cent on a small number of prorated lines. Real plan prices in whole dollars rarely produce an exact half cent, but storage packs combined with seat changes can.

### Failure 2: invoice email skipped billing contacts after the first one

- Test: `tests/unit/notifications/test_invoice_email.py::test_invoice_ready_goes_to_all_billing_contacts`
- What the test does: it creates an account with the Owner, one Billing admin and 5 billing contacts, then sends `invoice_ready`. It expects 7 recipients.
- What happened: 3 recipients. Only the first billing contact received the email.
- Cause: the recipient builder read a single contact address instead of the new list of up to 5.
- Fix: the Platform team changed the builder to read the full list and to remove duplicate addresses. The same builder is used for `payment_failed`, so that template was fixed at the same time.

Both fixes were merged on 2026-01-13 as commit `a41c9e2` plus two follow-up commits. The second run on the same day passed with 309 passed, 0 failed and 3 skipped.

## Which tests were skipped?

- `auth`: 1 test for SMS code delivery. It needs the SMS provider sandbox, which was under maintenance on the run date.
- Integration: 2 tests for ACH and SEPA bank transfers. The processor sandbox does not support bank transfers on the CI runner. These two are run by hand once per release in the billing manual suite (`TC-BILL-019`, `TC-BILL-020`).

No test was skipped to hide a failure.

## What risks were accepted?

- Bank-transfer payments (ACH, SEPA) are covered only by two manual cases, not by automated tests.
- The invoice email has no protection against being sent twice if the notification queue retries a send. This was noted in the run as a gap but not treated as a blocker. It became the root cause of INC-2026-001 on 2026-02-11, when invoice emails were sent twice to billing contacts for 3 hours 10 minutes. The fix (an idempotency key made of template, recipient and object ID) shipped in 2026.2.
