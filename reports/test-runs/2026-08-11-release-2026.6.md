# Test Run Report: Release 2026.6 (2026-08-11)

This report covers the test run at the code freeze for release 2026.6. The release shipped on 2026-08-18. It added audit log filters and CSV download, and 7-year audit log retention on Enterprise. It also carried the follow-up to INC-2026-004: an export that runs longer than 24 hours is marked `failed`. All data is fictional sample data.

## Did any automated test fail?

No. There were 0 failures in the freeze run.

Three defects were found and fixed earlier in the cycle, before the freeze, by tests written together with the feature. They are listed here because they show what the new tests protect against.

| Found on | Test | Defect | Fix |
|----------|------|--------|-----|
| 2026-07-29 | `tests/unit/audit/test_filters.py::test_filter_end_date_is_inclusive` | A filter ending on 2026-07-31 left out events from that day | The end of the range is now the end of the day in UTC |
| 2026-08-03 | `tests/unit/audit/test_retention.py::test_business_events_kept_one_year` | Business accounts were given the Enterprise retention of 7 years | Retention is now read from the plan table: Pro 90 days, Business 1 year, Enterprise 7 years |
| 2026-08-05 | `tests/unit/workspaces/test_export_timeout.py::test_export_at_exactly_24_hours_is_still_running` | An export was marked `failed` at exactly 24 hours instead of after 24 hours | The comparison was changed from "at least" to "longer than" |

All three were boundary mistakes: an end date, a plan boundary and a time limit.

## Which tests were skipped?

## How was the INC-2026-004 follow-up tested?

INC-2026-004 on 2026-07-22 left workspace exports stuck in `running` for 9 hours 40 minutes. The export worker had lost its job lease after the 2026.5 rewrite, and there was no timeout. The follow-up has 5 new unit tests in `tests/unit/workspaces/test_export_timeout.py` and 3 new integration tests.

- An export that has run for 23 hours 59 minutes is still `running`.
- An export that has run for longer than 24 hours is marked `failed`.
- A `failed` export does not block a new export for the same workspace.
- When a worker stops in the middle of a job, another worker takes over the lease.
- The requester is told when an export fails.

The process rule agreed after the 2026.5 run was applied here for the first time: the "worker dies in the middle" test existed before the freeze.

Manual case `TC-WS-017` repeated the incident on staging. A worker was stopped by hand during a 10 GB export. A second worker finished the job, and the status moved to `ready`. The case passed.

New manual cases in this run:

- `TC-SEC-027`: download the filtered audit log as CSV and open it in a spreadsheet.

Two observations were recorded without failing a case:

- A CSV with 250,000 rows took 41 seconds to prepare. The page shows a progress message, so the case passed. The Platform team opened a ticket to stream large downloads.
- An account on Free or Starter has no audit log. The page correctly shows an upgrade notice, and the API returns `ERR_PLAN_REQUIRED`.

## Was the release approved?

Yes. The decision was **Go**, with no conditions.

- Decision date: 2026-08-12, one day after the freeze. This was the shortest time between freeze and decision in 2026.
- Approved by: the release manager, the Platform team lead and the Accounts team lead.

The release was deployed to `us-east` on 2026-08-18, and to `eu-central` and `ap-south` one business day later.

## What should the next run improve?

1. Release 2026.7 makes webhooks generally available. The Platform team should write retry-timing and signature tests with the fake clock from the start. The 2026.5 run showed that real-time waits cause both slow tests and false failures.
2. Add a load check for audit CSV downloads above 100,000 rows.
3. Keep the count of permanently skipped tests at 5 or lower. A plan to run the UPI test against a local fake is owned by the Billing team.
