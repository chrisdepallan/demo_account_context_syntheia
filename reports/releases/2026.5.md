## What is new for customers?

### Workspace export as a queued job

The workspace export no longer runs inside the browser request. It runs in the background and the requester gets an email when it is done.

- Menu path: **Settings → Workspace → Export**. The Owner or an Admin starts the export.
- The page shows the status of the export. The user can close the browser; the export continues.
- When the export is finished, the requester receives the `export_ready` email with a download link.
- The download is a ZIP with JSON and the original files, as before.
- The link is valid for **7 days**. After that the export has the status `expired` and a new export is needed.

Why this changed: the old export was a single long download. For large workspaces it could break off when the connection or the session ended, and the user had to start again from zero. Since 2026.4, exports are also the way to move data to another region, so they have to be reliable.

### One export per workspace

Only one export per workspace can run at a time.

- While an export is `queued` or `running`, the **Export** button for that workspace is disabled.
- A second export can be started as soon as the first one is `ready`, `expired` or `failed`.
- Exports of different workspaces in the same account can run at the same time.

## What changed for admins and API users?

Export statuses in this release:

| Status | Meaning |
|--------|---------|
| `queued` | The export is waiting for a worker. |
| `running` | A worker is building the ZIP. |
| `ready` | The ZIP can be downloaded. The link is valid for 7 days. |
| `expired` | The 7 days are over. The ZIP was deleted. |
| `failed` | The export stopped with an error. A new export can be started. |

- Each export has an ID such as `exp_6J4D8S2A`. Support can look up an export by this ID in the admin console.
- Starting a second export for a workspace that already has one in `queued` or `running` is refused with `ERR_CONFLICT` (HTTP 409).
- Starting an export needs the permission `workspace.export`, which the Owner and Admins have.
- The audit log (Pro and above) records `export.started` when the export is requested and `export.downloaded` each time the ZIP is downloaded.
- An account in `read_only` can still export. Exports only read data.
- The design is recorded in ADR 0007, "Exports run as queued jobs", which replaces the synchronous export.

## Which fixes are included?

No incident follow-ups shipped in this release.

| Area | Fix |
|------|-----|
| Workspaces | File names with characters that are not allowed in ZIP archives are kept in the JSON and replaced by a safe name in the archive. Before, the export stopped at such a file. |
| Workspaces | The export includes files up to the maximum upload size of 5 GB. Before, files over 2 GB were skipped with a note in the JSON. |

## What do I need to do to upgrade or migrate?

Nothing is required. The new export is used automatically.

- Users who had an old export download in progress at deploy time had to start it again. This affected 6 downloads in `us-east` on 2026-07-07 and 2 in `eu-central` on 2026-07-08.
- Scripts that called the old export and waited for the file in the same request must change. The new flow is: start the export, wait for the status `ready`, then download.
- The content of the ZIP did not change. Tools that read the JSON files keep working.
- For a region move, plan for the export to take from a few minutes to several hours, depending on the size of the workspace.

## What is the rollback plan?

- **Queued export** is behind a feature flag. Turning the flag off brings back the old synchronous export. Exports that are `queued` or `running` at that moment are marked `failed` and their requesters are told to start again.
- The old export code stayed in the build as the rollback path until 2026.6 and was removed in 2026.7.
- **Full rollback**: deploy the 2026.4 build again. Target time is 30 minutes per region. The new export table is ignored by the old build.
- **Decision**: the release manager decides together with the on-call engineer. `eu-central` and `ap-south` are not deployed if `us-east` shows a problem on the first day.

No rollback was done. During INC-2026-004 the flag was considered and not used: new exports worked, and going back to the old export would have failed every export that was in progress.

## What changed in the release process after this release?

Since 2026.6 the test summary of every release report names an owning team and a repair date for each quarantined test. A release with a quarantined test in the area of its headline change needs the sign-off of the release manager and of the owning team's lead.
