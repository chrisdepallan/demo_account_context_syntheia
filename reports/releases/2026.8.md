## What is new for customers?

### Ownership transfer needs acceptance

A transfer of account ownership is now a request that the new Owner has to accept. Before this release the transfer took effect at once.

1. The Owner goes to **Settings → Account → Transfer ownership** and picks an existing Admin.
2. The chosen Admin receives the `ownership_transfer` email.
3. The Admin must accept within **7 days**. If not, the request expires and nothing changes.
4. On acceptance the Admin becomes the Owner, and the previous Owner becomes an Admin.

Why this changed: the Owner is the only role that can close the account, transfer it and, together with Billing admins, manage billing. Nobody should receive that role without knowing it. There is still exactly one Owner per account at every moment (ADR 0001).

### OIDC SSO

Workspaces on Business and Enterprise can now connect an identity provider with OpenID Connect (OIDC), as well as with SAML 2.0.

- Menu path: **Settings → Security → SSO**, then choose OIDC as the connection type.
- The Owner or Admin enters the provider's issuer URL and the client details, and copies the redirect URL shown on screen into the identity provider.
- The other steps are the same as for SAML: verify the email domain with the DNS TXT record `acme-verify=<token>`, select **Test connection**, then **Enable**.
- **Enforce SSO** works with an OIDC connection in the same way. The Owner keeps password + MFA as the break-glass login.

## What changed for admins and API users?

Ownership transfer:

- Only the Owner has the permission `account.transfer`. The target must be an Admin.
- The audit log records `ownership.transfer_requested` when the Owner sends the request and `ownership.transferred` when the Admin accepts.
- While a request is open, the Owner keeps all rights. Only one request can be open per account.
- The 7 days are exactly 7 × 24 hours from the request time in UTC. They are not counted in calendar days.
- The process for an Owner who cannot be reached did not change: an Admin contacts support, and it takes up to 5 business days.

OIDC:

- An OIDC connection has an ID in the same format as a SAML connection, for example `sso_7Q3W9E`.
- Turning SSO on writes `sso.enabled` to the audit log; turning on Enforce SSO writes `sso.enforced` and sends the `sso.enforced` webhook event.
- Existing SAML connections are not touched. The ACS URL and the Entity ID are unchanged.
- The 3-minute clock skew rule applies to SAML assertions. OIDC logins have their own token time check, and the 30-second clock drift alert from 2026.4 protects both.
- SCIM provisioning stays an Enterprise feature and works with SAML and OIDC connections.

## What are the known issues?

| Issue | Status |
|-------|--------|
| A transfer request cannot be sent to a Member. The Member must be made an Admin first. | By design. |
| If the chosen Admin is removed or loses the Admin role while a request is open, the request is cancelled without an email to the Owner. | Open. |
| The `ownership_transfer` email is sent once. There is no reminder before day 7. | Open. The Owner can cancel the request and send a new one. |
| A workspace has one SSO connection. Moving from SAML to OIDC means replacing the connection; SSO logins fail for the few minutes between the two. | Open. Do the change outside working hours. |
| One follow-up of INC-2026-006 is not finished: the review of per-region settings. Values that must never differ between regions become constants in code. | In progress, due 2026-12-15, planned for the first release of 2027. |

## What do I need to do to upgrade or migrate?

**Ownership transfer**

- Nothing is required. No transfer was in progress at release time, because transfers were immediate before.
- Owners who plan a handover should send the request at least 7 days before they leave and check that it was accepted.

**OIDC**

- Nothing is required for workspaces that stay on SAML.
- To move a workspace from SAML to OIDC:
  1. Set up the OIDC application in the identity provider first.
  2. If **Enforce SSO** is on, check that the Owner's break-glass login (password + MFA) works.
  3. Replace the connection under **Settings → Security → SSO** and select **Test connection**.
  4. Select **Enable**. The domain verification stays valid and is not repeated.

**API keys**

- Nothing is required. The 60-second rule for **Revoke** holds in every region.
- Customers in `ap-south` who revoked a key between 2026-10-10 and 2026-10-15 were contacted on 2026-10-19.

## What is the rollback plan?

- **Ownership transfer acceptance** is behind a feature flag. Turning it off returns to the immediate transfer. Requests that are open at that moment are cancelled, not completed, and both sides are emailed.
- **OIDC** is behind a feature flag. Turning it off hides the connection type for workspaces that have no OIDC connection. Workspaces that already use OIDC keep it; a login method in use is never removed by a rollback.
- **Key cache TTL** is not rolled back. A build with a configurable TTL must not go to production again. If the 2026.8 build has to be replaced, the TTL change is kept in the replacement build.
- **Full rollback**: deploy the 2026.7 build with the TTL change added. Target time is 30 minutes per region.
- **Decision**: the release manager decides together with the on-call engineer. `eu-central` and `ap-south` are not deployed if `us-east` shows a problem on the first day.

No rollback was needed.
