## What is new for customers?

### Require key expiry policy

Owners and Admins can stop the creation of API keys that never expire.

- Menu path: **Settings → Security → Require key expiry**.
- When the policy is on, the option "Never" is hidden in **Settings → API keys → Create key**. The remaining choices are 30, 90, 180 or 365 days.
- The policy is off by default.
- The policy is available wherever API keys are available: Starter and above.

### Key expiry warning email

The Owner now receives the `key_expiring` email **14 days** before an API key expires.

- The email names the key and shows its last 4 characters and its expiry date. It never contains the key itself.
- It links to **Settings → API keys**, where the key can be rotated with **Rotate**. After a rotation the old key keeps working for 24 hours.
- A key with an expiry of 30 days gets its warning on day 16 after creation.

## What changed for admins and API users?

- Turning **Require key expiry** on or off writes a `policy.changed` event to the audit log (Pro and above).
- With the policy on, an API call or dashboard action that tries to create a key without an expiry is refused with `ERR_VALIDATION` (HTTP 400).
- Existing keys that never expire are not changed and keep working when the policy is turned on. They are marked "No expiry" in the key list so that an Admin can find and rotate them.
- Rotating a key while the policy is on needs an expiry for the new key.
- Key rules that did not change: prefixes `acme_live_` and `acme_test_`, up to 25 active keys per workspace, revoke takes effect within 60 seconds.
- The `key_expiring` email goes to the Owner only, not to Admins and not to billing contacts.

## What do I need to do to upgrade or migrate?

Nothing is required. The policy is off until an Owner or Admin turns it on.

Recommended steps for accounts that want every key to expire:

1. Turn on **Settings → Security → Require key expiry**.
2. Open **Settings → API keys** and look for keys marked "No expiry".
3. Select **Rotate** for each one and choose an expiry. Update the integration within 24 hours, while the old key still works.

Notes for the notification change:

- The idempotency key needs no action from customers.
- A resend that a user asks for, such as resending an invitation, is not blocked. It is a new send with a new object ID.
- The database change is additive: one new table that stores accepted idempotency keys.

## What is the rollback plan?

- **Require key expiry** is behind a feature flag. Turning the flag off hides the toggle and allows "Never" again. Keys created under the policy keep their expiry.
- **Key expiry warning email** can be turned off by disabling the `key_expiring` template. No other template is affected.
- **Idempotency key** has its own flag. If it is turned off, retries for the billing-contact step are turned off with it, which returns the system to its state between 2026-02-11 and 2026-03-03. Duplicates must not come back through a rollback.
- **Full rollback**: deploy the 2026.1 build again. Target time is 30 minutes per region. The new table is ignored by the old build.
- **Decision**: the release manager decides together with the on-call engineer. `eu-central` is not deployed if `us-east` shows a problem on the first day.

No rollback was needed.
