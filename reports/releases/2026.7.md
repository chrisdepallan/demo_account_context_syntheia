## What is new for customers?

### Webhooks are generally available

Webhooks send an HTTP request to a customer's server when something happens in the account. They were in beta for 46 accounts before this release. Now every plan from Starter up can use them.

| Plan | Webhook endpoints |
|------|-------------------|
| Free | 0 |
| Starter | 2 |
| Pro | 5 |
| Business | 20 |
| Enterprise | 50 |

Owners and Admins register an endpoint with a URL and a list of events. Each endpoint has an ID such as `wh_8C2V6B4N`.

The 10 events:

| Event | Sent when |
|-------|-----------|
| `account.state_changed` | The account moves between states, for example `active` to `past_due` |
| `member.invited` | An invitation is sent |
| `member.removed` | A member is removed |
| `invoice.paid` | An invoice is paid |
| `invoice.payment_failed` | A charge fails |
| `refund.succeeded` | A refund is confirmed by the processor |
| `api_key.created` | An API key is created |
| `api_key.revoked` | An API key is revoked |
| `export.ready` | A workspace export is ready to download |
| `sso.enforced` | **Enforce SSO** is turned on |

### `Acme-Signature` header

Every webhook request is signed, so that the receiver can check that it comes from Acme Cloud and was not changed on the way.

- The signature is an HMAC-SHA256 of the request body. It is sent in the `Acme-Signature` header.
- Each endpoint has its own signing secret. It is shown once when the endpoint is created, like an API key.
- The receiver calculates the same HMAC with its copy of the secret and compares. A request with a missing or wrong signature should be rejected.

## What changed for admins and API users?

Delivery rules:

- The receiver must answer within **10 seconds** with a 2xx status. Anything else counts as a failed delivery.
- A failed delivery is retried **6 times** over **24 hours**: after 1 minute, 5 minutes, 30 minutes, 2 hours, 8 hours and 24 hours.
- An endpoint is disabled after **3 days** of continuous failures. The Owner or an Admin turns it on again after fixing the receiver.
- The same event can arrive more than once, for example when the receiver answered after 10 seconds. Receivers should use the event's ID to ignore repeats.

Other points:

- Registering more endpoints than the plan allows is refused with `ERR_LIMIT_EXCEEDED` (HTTP 409). Free accounts get `ERR_PLAN_REQUIRED` (HTTP 403).
- Managing endpoints needs the Owner or Admin role.
- Webhook payloads never contain secrets: no API key, no password, no payment data. An `api_key.created` event carries the key ID (for example `key_5T9W3E7Y`), not the key.
- Webhook deliveries do not count against the API rate limit.
- The design is recorded in ADR 0009, "Webhook delivery with signed payloads and six retries".

## What are the known issues?

| Issue | Status |
|-------|--------|
| Beta deliveries were not signed. Receivers written during the beta do not check a signature. | They keep working, because an extra header is harmless. Beta customers should add the check. |
| A disabled endpoint does not send an email to the Owner. The state is visible in the endpoint list. | Open. |
| Events are not replayed after an endpoint is turned on again. Events from the time it was disabled are lost for that endpoint. | By design. Use the REST API to read the current state. |
| There is no webhook event for a failed export. | Open. `export.ready` is the only export event. |

## What do I need to do to upgrade or migrate?

**New webhook users**

1. Register an endpoint and choose the events.
2. Store the signing secret in a secrets manager. It is shown once.
3. Check the `Acme-Signature` header on every request.
4. Answer within 10 seconds. Do slow work after answering.

**Beta users (46 accounts)**

- Existing endpoints were kept. Each one received a signing secret at release, which the Owner can show once.
- Deliveries are signed from 2026-09-29 in `us-east` and from 2026-09-30 in `eu-central` and `ap-south`.
- Beta accounts on Starter with more than 2 endpoints keep their existing endpoints, but cannot add new ones until they are at or below the plan limit. This affects 3 accounts.

**Database failover**

- No action is needed from customers. During a quarterly failover test, requests to a region can be slow or fail for up to about 1 minute. Tests run outside business hours for the region and are announced on `https://status.acme-cloud.example`.

## What is the rollback plan?

- **Webhooks** stay on for the 46 beta accounts in every case. General availability is a flag per plan and can be turned off for accounts that have no endpoint yet.
- **Signing** is not rolled back. A receiver that checks signatures would reject unsigned requests.
- **Reconnect without restart** has a flag. Turning it off returns to the old behaviour, where a restart is needed after a promotion; the runbook `docs/runbooks/region-failover.md` covers both cases.
- **Maintenance mode time limit** can be raised or turned off by the Platform team for a planned long maintenance. This needs a second engineer's approval.
- **Full rollback**: deploy the 2026.6 build again. Target time is 30 minutes per region. The old synchronous export does not come back; it was already off in 2026.6.
- **Decision**: the release manager decides together with the on-call engineer. `eu-central` and `ap-south` are not deployed if `us-east` shows a problem on the first day.

No rollback was needed.
